# Screening

`screening:50051` регистрирует [ScreeningQueryService](../../contracts/grpc/v1/screening.proto)
и gRPC Health. По умолчанию `GetSurvey` возвращает демонстрационную анкету
из `survey.json`. Локальный режим `SCREENING_MOCK=1` включает обработку
команд и чтение сессий, результатов и операций из памяти.

[Запуск стенда](../../infra/README.md)

В Docker файлы сервиса размещаются в пакете `service`, запуск выполняется
командой `python -m service.main`. Из корня репозитория модуль запускается
через `python -m services.screening.main` с подготовленными зависимостями
и Protobuf-модулями, как для локальных тестов ниже.

## Версионируемые правила расчёта

Полный пример формата с синтетическими вопросами находится в
[`tests/fixtures/example_rules.json`](tests/fixtures/example_rules.json).
Конфигурации хранятся в UTF-8. Коды сравниваются буквально, включая регистр и
алфавит. Например, латинская `B` и кириллическая `В` — разные коды.

| Поле | Значение |
| --- | --- |
| `id`, `weights_version` | Код шкалы и версия правил. Вместе идентифицируют одну неизменяемую конфигурацию. |
| `blocks[].code`, `blocks[].questions` | Уникальный код блока и его вопросы. Для общей шкалы используются блоки А/Б/В/Г. |
| `questions[].code`, `text`, `required`, `type` | Код вопроса, уникальный в пределах шкалы, текст, явный булев признак обязательности и тип `boolean` или `single_choice`. |
| `weights`, `options` | У `boolean` коды ответа `yes` и `no`, а их веса задаются в `weights`. Для `single_choice` каждый вариант содержит уникальный в пределах вопроса `value`, подпись `label` и вес `weight`. Все ответы в блоках подсчёта требуют целого неотрицательного веса. |
| `scoring.sum_blocks` | Коды блоков, веса ответов в которых входят в сумму. Для общей шкалы сюда входят А, Б и Г. |
| `scoring.thresholds` | Соответствие «уровень → [нижняя, верхняя граница]». Границы включены, `null` означает открытый верх. Диапазоны идут без разрывов и пересечений, начиная с 0 и покрывая максимальную сумму. Максимум — сумма наибольших весов каждого вопроса в блоках подсчёта. Код `red_flag` зарезервирован для срочного результата. |
| `scoring.outcome_recommendations` | Для каждого уровня из `thresholds` указан непустой список кодов рекомендаций. |
| `scoring.red_flags[]` | Уникальный `code`, условие `when` с полями `question_code` и `option_code` и непустой список `recommendation_codes`. Условие описывает совпадение с одним вариантом ответа. Приоритет флагов не задаётся. Шкала без флагов указывает пустой массив. |
| `recommendations[]` | Уникальный код `code` и текст `text` каждой рекомендации. |

Максимальная сумма ограничена значением `2 147 483 647`, чтобы баллы
помещались в поля `int32` контракта Screening v1.

[`rules.py`](rules.py) проверяет файл до регистрации. Ошибка `RuleConfigError`
содержит `version` и `field`, например
`v1` и `$.scoring.red_flags[0].when.option_code`. Для синтаксической ошибки
JSON указывается строка и столбец, а версия недоступна до успешного разбора.

[`registry/BaseRegistry`](registry/base.py) задаёт интерфейс публикации и чтения
версий. [`LocalRegistry`](registry/local.py) реализует его в памяти процесса.
Хранилище сессий зависит от `BaseRegistry`; другие backend-реализации
подключаются через этот интерфейс. Загрузка и валидация JSON находятся в `rules.py`.

`LocalRegistry.publish(path)` регистрирует новую версию и делает её текущей
для этой шкалы. `get(id, version)` получает точную версию, а `get(id)` —
текущую. Ошибка публикации не меняет реестр. При изменении любого поля
создайте файл с новым `weights_version`. Повторная загрузка идентичного
файла сохраняет текущую версию. Реестр хранит загруженные определения в
памяти процесса.

В [черновике красных флагов](rule_configs/red_flags.draft.json) приведены
семь записей из `red_flags.items` исходного JSON и связанные тексты действий.
Каждое условие представлено положительным ответом на булев пункт. Для
примера этим пунктам задано `required: false`. Статус источника —
`pending_curator_approval`. Этот файл содержит только фрагмент правил.
Тест проверяет его в составе синтетической анкеты.

### Расчёт и объяснение

[`calculate_result`](scoring.py) принимает проверенные правила конкретной
версии и словарь сохранённых ответов по кодам вопросов. Значение ответа —
`True` или `False` для булева вопроса и код варианта для вопроса с выбором.
Некорректный ответ вызывает `AnswerError` с кодом вопроса.

1. Функция проверяет ответы, находит пропущенные обязательные вопросы и
   считает вклад каждого сохранённого ответа в блоках подсчёта, включая
   нулевой вклад. Пропуск необязательного вопроса даёт ноль баллов.
2. Если сработал хотя бы один флаг, уровень — `red_flag`. Объяснение содержит
   код, вопрос и вариант ответа для каждого флага. Для продолженной сессии
   можно передать сохранённые коды флагов той же версии через
   `previous_red_flag_codes`. Поле `matched_current_answer` показывает,
   присутствует ли сработавший ответ в текущем наборе.
3. При пропущенных обязательных ответах `total_score` отсутствует, а суммы
   блоков отражают частичный расчёт. Без сработавших флагов такой результат
   получает причину `incomplete` и пустой уровень.
4. Для полной анкеты функция возвращает итоговую сумму. Если флагов нет,
   сумма определяет уровень, а `matched_range` показывает его диапазон.
   Результат содержит код шкалы, версию правил и рекомендации для исхода.

```python
from services.screening.rules import load_rules
from services.screening.scoring import calculate_result

rules = load_rules("services/screening/tests/fixtures/example_rules.json")
result = calculate_result(rules, {"A1": "zero", "Б1": True, "В1": False, "Г1": True})
print(result.level, result.total_score, result.matched_range)
# medium 10 (5, 10)
```

## Завершение скрининга на моках

В режиме мока `GetSurvey` отдаёт синтетическую шкалу `example/v1`. Обработчик
читает `ScreeningCommand` из `dev.screening.commands.v1`. В `StartScreening`
клиент передаёт точную версию анкеты, версию дисклеймера и факт согласия.
`SaveAnswer` обновляет ответ по коду вопроса. `CompleteScreening` берёт
закреплённые правила и сохранённые значения. Из `GetOperation` можно
получить исход и версии изменённых ресурсов.

Хранилище реализует [`ScreeningStore`](storage.py) с транзакционным интерфейсом
для чтения правил, ответов и записи результата. Каждое успешное изменение
сессии или ответа записывает в outbox событие `SessionChanged` с новой ревизией
сессии. При создании или обновлении результата в той же транзакции добавляется
`ResultChanged` со снимком расчёта. При успешном завершении транзакция также
фиксирует статус `completed` и исход операции. Оба события используют
[контракт событий Screening v1](../../contracts/events/v1/screening.proto).
Если в команде пустой `correlation_id`, события используют `operation_id`.
В неполной анкете без флага сохраняется черновик. При срабатывании флага
результат сразу сохраняется с уровнем `red_flag`. После продолжения и
завершения он сохраняет идентификатор и получает новую ревизию.

События хранилища в памяти доступны через `InMemoryScreeningStore.outbox_events()`
в виде бинарных `ScreeningEvent`. Данные хранятся до остановки процесса.
Локальный режим с обоими хранилищами предназначен для синтетических данных
и проверяет владельца по тестовому `ActorContext`.

На отдельном локальном стенде с подготовленным окружением Compose включите
обработчик команд при запуске Screening.

```bash
make migrate
docker compose run --build --rm -e SCREENING_MOCK=1 screening
```

### PostgreSQL

Для записи синтетических сессий в PostgreSQL на локальном стенде выберите
`SCREENING_STORAGE=postgres`. При старте Screening регистрирует
`example/v1` с дисклеймером `demo-v1`. Подключение использует `PGHOST`
и пароль роли `mis_screening_app` из секрета Compose.

```bash
make migrate
docker compose run --build --rm -e SCREENING_MOCK=1 -e SCREENING_STORAGE=postgres screening
```

Адаптер использует `pg8000` из существующего lock-файла и миграции
[`001`](../../infra/db/common/001_messaging.sql) и
[`002`](migrations/002_screening.sql). В `inbox_messages.outcome`
хранятся исходы по `operation_id` и служебное состояние изменённой
ревизии сессии, включая время завершения и признак прерывания.
При конфликте `command_id` исход новой операции добавляется к записи
команды, а первоначальный исход сохраняется.
Старые записи inbox с `operation_id` сохраняют этот идентификатор,
даже если в них отсутствует ответ для повторной выдачи.
В PostgreSQL передавайте UUIDv7 для субъекта, команды, операции и
непустого `correlation_id`.

При старте выбирается актуальный дисклеймер для указанной версии весов.
Сессия хранит ссылку на точную пару версий весов и дисклеймера. Варианты
правил и текста регистрируются новыми строками, текущая анкета
выбирается по последнему опубликованному UUIDv7. Текст хранится в
`questionnaire_versions.definition.disclaimer` и возвращается в поле
`Survey.disclaimer`.

Финальная ревизия добавляется до перевода сессии в `completed`.
Адаптер фиксирует ревизию, статус, исход операции, inbox и outbox в одной
транзакции. Для старой SQL-ревизии, в которой нет полноценного снимка,
чтение возвращает `FAILED_PRECONDITION`, а команда изменения сохраняет
отказ `RESULT_SNAPSHOT_UNAVAILABLE`.

### Локальные тесты

Загрузчик и чистый расчёт используют стандартную библиотеку Python. Для
полного набора нужны зависимости из существующего
[`service-runtime/uv.lock`](../../packages/service-runtime/uv.lock) и сгенерированные
модули Protobuf. Команды Bash выполняются из корня репозитория. Для
установки `uv` при необходимости используйте `python -m pip install uv`.

```bash
uv sync --project packages/service-runtime --locked --no-install-project
screening_python="$PWD/packages/service-runtime/.venv/bin/python"
screening_proto="$(mktemp -d)"
"$screening_python" -m grpc_tools.protoc -I. \
  --python_out="$screening_proto" --grpc_python_out="$screening_proto" \
  contracts/*/v1/*.proto
PYTHONPATH="$screening_proto:$PWD/packages/service-runtime${PYTHONPATH:+:$PYTHONPATH}" \
  PYTHONUTF8=1 "$screening_python" -m unittest discover -s services/screening/tests -v
```

Эта команда запускает тесты мока и пропускает интеграционные тесты
PostgreSQL. Транспортный тест использует gRPC на локальном порту,
выделенном системой. Для регрессии BFF выполните команды из
[README BFF](../bff/README.md).

Для полного прогона с Docker выполните из корня:

```bash
uv run --project packages/service-runtime --locked --no-install-project python services/screening/tests/run_postgres.py
```

Скрипт генерирует Protobuf во временном каталоге, создаёт отдельный
PostgreSQL на localhost, применяет SQL миграций и запускает проверки под
ролью приложения. Он проверяет повтор команды, конкурентное завершение,
точные ревизии и откат всех записей после ошибки outbox. Временный
контейнер удаляется при остановке.

Для отдельных проверок формата и чистого расчёта достаточно системного Python.

```bash
python -m unittest discover -s services/screening/tests -p test_rules.py -v
python -m unittest discover -s services/screening/tests -p test_scoring.py -v
```

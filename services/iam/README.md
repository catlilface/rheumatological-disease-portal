# IAM: гостевые и служебные сессии (MIS-30)

BFF вызывает [IamService](../../contracts/grpc/v1/iam.proto) по **mTLS**. IAM принимает прикладные RPC только от BFF; наличие идентификаторов, сетевой доступ или служебный сертификат сами по себе не дают прав на анкету. Единственный источник сессий — PostgreSQL `mis_iam`. У гостя собственный UUIDv7, нет email и нет роли. У служебного аккаунта одна активная роль: `editor` или `admin`.

| Через BFF (`/api/v1`) | RPC | Поведение |
|---|---|---|
| `POST /auth/guest-sessions` | `CreateGuestSession` | Создаёт гостя и независимую сессию. Повтор `Idempotency-Key` без соответствующей текущей access-cookie не возвращает токены. |
| `POST /auth/session` | `SignInStaff` | Проверяет HMAC нормализованного email, scrypt-хеш пароля, блокировку и роль. Неверные данные не раскрывают наличие аккаунта. |
| `GET /auth/session` | `Authenticate` | Проверяет предъявленный access, состояние семьи и актуальную роль в БД. Идентификаторы в заголовках/JSON не участвуют. |
| `POST /auth/session/refresh` | `RefreshTokens` | Меняет обе cookie, оставляет тот же субъект и сессию. Клиенту достаточно refresh-cookie, в том числе после истечения access. |
| `DELETE /auth/session` | `EndSession` | Отзывает семью до ответа `204`; следующая проверка старого access/refresh отклоняется. Другие сессии не закрываются. |

Access — **168 часов**, refresh — не позже **30 дней с создания**, граница срока не включается. При ротации access ограничивается остатком жизни сессии. Использованный refresh хранится как дайджест, чтобы его повтор (даже с тем же ключом запроса) отзывал семью. Ротации одной семьи сериализуются блокировкой строки; клиент должен объединять параллельные обновления, а не повторять старый refresh. Потерянную гостевую cookie нельзя восстановить по ID анкеты.

Обе cookie — `HttpOnly; Secure`, токены не возвращаются в HTTP JSON и не помещаются в Kafka. Для записи нужны разрешённый `Origin` и `X-Portal-Request: 1`; для гостя и refresh также `Idempotency-Key: <UUID>`. Политики SameSite и пути cookie — в [OpenAPI](../../contracts/http/bff-v1.openapi.yaml). В браузере нужен HTTPS. IAM генерирует непрозрачные секреты с раздельными HMAC-доменами; в БД нет открытых токенов, email и паролей.

`CheckAccess` исполняется для конкретного запроса BFF, не выдаёт переносимых разрешений и не кешируется. BFF сверяет владельца в своём хранилище, IAM проверяет живую пару subject/session и разрешённое гостевое действие; неизвестное действие и чужой ресурс закрыты. Решение записывается в `access_audit` без медицинского содержимого и токенов. При отсутствии ответа IAM — `503 AUTHORIZATION_UNAVAILABLE`, без перехода к моку.

## Запуск и проверка

Из корня: `make up`. `make prepare` создаёт в приватном `MIS_SECRET_DIR` ключ IAM и отдельные TLS-комплекты IAM/BFF (CA и сертификаты **только для стенда**, на год). BFF не получает ключ IAM, пароль БД или ключ сервера. Сохраняйте секреты вместе с состоянием стенда; для production нужны управляемые PKI, ротация, ограничение частоты логина и внешний HTTPS.

Создать служебную учётную запись на новом стенде: `docker compose exec iam python -m service.provision editor` (либо `admin`). Email и пароль вводятся интерактивно; предустановленного логина нет. Публичного API регистрации нет.

Проверки **на одноразовом стенде с синтетическими данными**:

```sh
docker compose exec -T iam python -m unittest -v service.tests.test_sessions service.tests.test_bff
python3 infra/k8s/check-http.py http://127.0.0.1:8000
bash infra/check-transport.sh compose
```

Первая команда проверяет настоящие транзакции PostgreSQL, включая конкурентную ротацию; сроки проверяются с управляемыми часами без ожидания. HTTP-тест также проверяет вход администратора и подстановку известных `subject_id` и `session_id` другого гостя. Вторая проходит по HTTP → BFF → IAM, включая отказ чужому гостю и немедленный отзыв. Третья проверяет в том числе отказ gRPC-клиенту без клиентского сертификата.

Предметные ресурсы BFF пока синтетические и хранятся в памяти. Здесь нет кабинета пациента, переноса владения, API управления ролями, реальных Kafka-воркеров с повторной авторизацией, WSS или потокового доступа к файлам. Эти гарантии MIS-23 не следуют из тестов жизненного цикла сессий.

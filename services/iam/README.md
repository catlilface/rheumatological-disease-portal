# Сессии и доступ к порталу

Браузер обращается к `/api/v1` через BFF. IAM в `mis_iam` хранит субъекты, scrypt-хеши паролей, HMAC нормализованных email, роли, хеши access/refresh и аудит решений (без медицинского содержимого). На запись нужны допустимый `Origin` и `X-Portal-Request: 1`. Токены находятся **только в cookie**, не в JSON или Kafka. Для браузера используйте HTTPS (для локального Chrome допустим localhost).

| Запрос | Эффект |
|---|---|
| `POST /auth/guest-sessions` | Новый `guest`, без email и роли. `Idempotency-Key: <UUID>` не заменяет cookie при повторе. |
| `POST /auth/registrations` | Email, пароль (12–256 символов), `medical_data_consent: {accepted: true, version: …}` и UUID в `Idempotency-Key`. Версия — из `GET /auth/medical-data-policy`. Создаёт только `patient`, `kind=member` в браузерном контракте; поля `role`/`subject_id` недопустимы. С действующей гостевой cookie сохраняет владельца результатов, отзывает гостевые токены и выдаёт новую сессию. Без доказательства владения данные другого гостя не переносятся. |
| `POST /auth/session` | Вход зарегистрированного пациента, редактора или администратора по email и паролю. |
| `GET /auth/session` | Текущая роль из БД, срок сессии. |
| `POST /auth/session/refresh` | UUID ключ + refresh-cookie; ротация **обеих** cookie с тем же субъектом/семьёй. |
| `DELETE /auth/session` | Отзыв текущей семьи сессии и очистка cookie. |
| `DELETE /me/medical-data-consent` | Пациент отзывает согласие во всех сессиях, в том числе будущих. Повтор безопасен. Вход и собственный скрининг остаются доступны; медицинские данные кабинета — нет. |
| `PUT /admin/account-role` | `{email, role}`: только действующий `admin` может назначить `admin`, `editor` или вернуть `patient` пользователю с согласием. Нельзя менять свою роль. Сессии целевого аккаунта отзываются; нужен новый вход. |

`portal_session` — `HttpOnly; Secure; SameSite=Lax`, до 7 дней. `portal_refresh` — `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth/session`, максимум 30 дней с создания семьи. Повтор использованного refresh отзывает семью. Фронтенд на `401 SESSION_REQUIRED` проверяет, не обновилась ли сессия параллельно, делает refresh и один раз повторяет запрос. Обновление объединяется в одной вкладке и сериализуется между вкладками в браузерах с Web Locks. Ошибка сети или IAM не является основанием создать нового гостя.

## Роли и данные

- `guest` и `patient` могут пройти скрининг, читать **свои** результаты и получить демонстрационное пояснение или PDF своей версии результата. Врачебный отчёт по данным кабинета требует действующего согласия как при заказе, так и при чтении или скачивании. Статьи, маршрут к врачу и определение анкеты публичны.
- Только `patient` имеет кабинет: `/me/onboarding` (имя, диагноз, назначения), лекарства, дневник, напоминания и `GET /me/screening-results?limit=20&offset=0` (все версии, от новых к старым по идентификатору результата и версии). В UI `/cabinet` есть вход, профиль, лекарства и ссылки на результаты. Формы регистрации нет.
- Ни `editor`, ни `admin` не получает чужие медицинские данные по роли. API редактирования статей здесь не включён.
- Кабинеты и результаты находятся в отдельном bbolt-файле на постоянном томе BFF (`patient_archive`, в Kubernetes — PVC). Архив предназначен для **одного пишущего экземпляра**; не масштабируйте Deployment горизонтально без замены хранилища. Команды кабинета сохраняют изменения, ключ повтора и статус операции одной транзакцией архива. Незавершённые анкеты, остальные операции и временные PDF BFF по-прежнему в памяти. Для реальных данных требуются резервирование, защищённые тома и политика удаления.

BFF делает `Authenticate` и на приватном ресурсе `CheckAccess` по действующему access-токену, субъекту/сессии, операции и владельцу из собственного хранилища. Подстановка ID не авторизует. Нет ответа IAM — нет доступа. Приватный gRPC screening (при `SCREENING_MOCK=1`) принимает только BFF по mTLS, ожидает metadata `cookie: portal_session=…`, **сам** вызывает IAM по mTLS со своим сертификатом, проверяет роль, контекст и владельца записи. IAM разрешает screening только `Authenticate`. Статические Files/Reporting пока не отдают приватных данных, AI не имеет API; BFF не проксирует в них медицинское содержимое. Транспорт развития не следует путать с полной реализацией этих сервисов.

## Начальный администратор

До `make up` укажите в локальном `.env` **оба** `IAM_ADMIN_EMAIL` и `IAM_ADMIN_PASSWORD` (12–256 символов). В репозитории нет значений по умолчанию. Compose передаёт их только IAM. В Kubernetes используется необязательный Secret `iam-bootstrap` с ключами `email`, `password`. При первой успешной инициализации аккаунт и маркер записываются атомарно. Смена переменных и рестарт не сбрасывают пароль и не создают второго администратора. После bootstrap секрет можно убрать. Сохраните ключ IAM вместе с состоянием стенда; для production нужны управляемая PKI и ограничение частоты входа/регистраций.

## Проверки (одноразовый Compose с синтетическими данными)

```sh
make up
docker compose exec -T iam python -m unittest -v service.tests.test_policy service.tests.test_sessions service.tests.test_bff
docker compose run --rm --no-deps -v "$PWD/.secrets/portal-tls-v2/bff:/run/test-bff-tls:ro" screening python -m unittest -v service.tests.transport_e2e
(cd services/bff && go test -race ./...)
(cd frontend && npm ci && npm test && npm run test:patient-e2e) # локальный Google Chrome, localhost:8080
```

Каталог второго клиентского сертификата в команде выше монтируется **только в одноразовый тестовый процесс**, не в рабочий screening. Протоколы: [HTTP](../../contracts/http/bff-v1.openapi.yaml), [gRPC](../../contracts/grpc/v1/iam.proto).
